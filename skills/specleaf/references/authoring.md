# 为 SpecLeaf 编写 OpenAPI

## 确定修改来源

- 优先沿用项目现有契约、OpenAPI 版本、目录结构和文档命令。先确认输入是完整契约还是被引用的模型、路径片段。
- 若 OpenAPI 由框架或工具生成，优先修改对应的路由定义、注解或生成器扩展配置，再按项目命令生成契约；直接修改生成产物可能在下次生成时丢失。扩展配置的写法取决于项目使用的框架，最终检查输出的字段层级和取值。
- 接口路径、参数、响应和鉴权以用户需求及已有实现为依据。代码可以提供接口结构，但不能单独证明接口已经测试或发布；状态按 [扩展字段规则](extensions.md) 处理。

## 组织契约

- 支持本地 OpenAPI 3.0 / 3.1 YAML 或 JSON。沿用原版本的 Schema 语法，例如 3.0 的 `nullable: true` 与 3.1 的包含 `null` 的类型联合不能机械互换。
- 单个完整契约直接作为 CLI 输入。多个独立模块各有自己的 `info`、`paths`、服务地址、鉴权和模型；每个模块目录只放一个 `openapi.yaml`、`openapi.yml` 或 `openapi.json` 入口，再传公共目录汇总。
- 模型片段采用 `models.yaml` 等非入口名称，避免被目录扫描识别为独立模块。`$ref` 相对包含它的文件解析，使用本地文件或内部 JSON Pointer。不要为了汇总文档手动合并模块或重命名跨模块同名模型。
- 新建时可参考 [模板](../assets/openapi.yaml)。模板的接口、模型、示例数据和 `draft` 状态只用于演示，按实际需求替换；状态未知且无项目约定时省略该字段。

## 填写展示内容

- 用 `info` 描述契约，用 `tags` 组织接口；没有 tags 的接口会归入“未分组”。保留已有 tag 和 `operationId` 的命名约定。
- SpecLeaf 展示契约中写明的原始示例，不按 Schema 自动补样例。需要示例时，在对应参数、媒体类型或 Schema 的示例字段中提供与定义一致的数据；`examples` 与 `example` 按所用 OpenAPI 版本及对象规则填写。
- 服务地址和鉴权使用标准 `servers`、`security` 与 `components.securitySchemes`。操作级 `security: []` 表示该接口无需鉴权，仅在符合实际要求时使用。
- `x-api-status` 及其他扩展的层级、类型和语义见 [扩展字段规则](extensions.md)。新增扩展前确认项目约定；保留任务范围外的已有扩展。

## 检查与交付

1. 检查本次修改的引用能解析、模板演示内容已按需求替换、示例与 Schema 一致。
2. 检查 `x-api-status` 是否位于 Operation、是否为允许的小写字符串；若与 `deprecated: true` 冲突，按实际生命周期修正。字段默认可选，只有项目明确要求时才检查必填。对已有错误值，不凭猜测替换业务状态。
3. 优先运行项目已有的 OpenAPI 校验或 lint 命令；若项目配置了扩展字段规则，一并执行。SpecLeaf 当前没有独立的 `check` / `lint` 子命令，HTML 生成成功也不代表完整语义校验通过。
4. 交付契约文件、修改范围和实际验证结果；未运行独立校验时如实说明。需要生成 HTML 时，回到 [SKILL.md](../SKILL.md) 的生成流程。
